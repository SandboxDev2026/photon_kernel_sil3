# PhotonBox 合规建设三阶段路线图

**版本**: 1.0
**生效日期**: 2026-09-05
**总周期**: 12 个月
**目标**: 通过 SOC 2 Type II 或 ISO 27001 认证，完成独立第三方安全审计

---

## 路线图总览

| 阶段 | 时间 | 主题 | 核心目标 | 关键交付物 |
|------|------|------|---------|-----------|
| **第一阶段** | 1-3 个月 | 打好地基 | 补全安全文档、生成 SBOM、定义漏洞 SLA | 信息安全政策、安全编码规范、漏洞修复 SLA、SBOM |
| **第二阶段** | 3-6 个月 | 硬化流程 | 固化证据、风险评估、第三方预审计 | 审批记录系统、风险评估报告、预审计报告 |

## 第一阶段：打好地基（1-3 个月）

### 阶段目标
建立安全管理的基础文档和工具，确保项目有明确的安全政策、编码规范、漏洞管理流程和软件物料清单。

### 1.1 补全安全文档

#### 1.1.1 《信息安全政策》
- **状态**: ✅ 已完成 (`docs/security/INFORMATION_SECURITY_POLICY.md`)
- **内容**:
  - 安全原则（纵深防御、最小权限、默认为安全、可审计性、不可信默认）
  - 数据分类与保护（机密/敏感/内部/公开四级）
  - 密钥管理（禁止硬编码、外部注入、定期轮换）
  - 访问控制（角色定义、认证要求、权限审查）
  - 沙盒安全政策（任务分级、强隔离要求、网络安全）
  - 漏洞管理政策（分级、SLA、响应流程、披露政策）
  - 变更管理政策（代码合并、生产发布、安全配置变更）
  - 事件响应政策（分级、流程、证据保全）
  - 合规要求（适用法规、认证目标、审计要求）
- **负责人**: 项目维护团队
- **审批**: 项目负责人

#### 1.1.2 《安全编码规范》
- **状态**: ✅ 已完成 (`docs/security/SECURE_CODING_STANDARDS.md`)
- **内容**:
  - 通用安全原则（输入验证、输出编码、错误处理、资源管理）
  - C++ 安全编码规范（内存安全、输入验证、系统调用安全、并发安全、加密安全、编译安全）
  - Python 安全编码规范（危险函数禁用、输入验证、子进程安全、网络安全、序列化安全、日志安全）
  - 沙盒特定安全规范（命名空间隔离、cgroup 资源限制、Landlock 文件系统限制、能力删除）
  - 代码审查安全检查清单（7 大类 40+ 检查项）
  - CI/CD 安全检查（必须通过的检查、定期运行的检查）
  - 违规处理（等级、处理措施）
- **负责人**: 开发团队
- **培训**: 所有开发者必须接受安全编码培训

#### 1.1.3 其他文档
- **漏洞修复 SLA**: ✅ 已完成 (`docs/security/VULNERABILITY_SLA.md`)
- **安全自评估报告**: ✅ 已完成 (`docs/audit/SECURITY_SELF_ASSESSMENT.md`)
- **生产上线检查清单**: 已有 (`PRODUCTION_CHECKLIST.md`)
- **安全边界声明**: 已有 (`docs/SECURITY_BOUNDARY.md`)
- **应急响应 runbook**: 已有 (`docs/ops/circuit_breaker_runbook.md`)

### 1.2 生成 SBOM（软件物料清单）

#### 1.2.1 SBOM 生成
- **状态**: ✅ 已完成 (`sbom.cdx.json`)
- **格式**: CycloneDX 1.5
- **工具**: 手动生成（环境无 syft/cdxgen，生产环境建议使用 syft）
- **内容**:
  - 16 个组件（Python 依赖 8 个 + C++ 依赖 8 个）
  - 依赖关系图
  - 已知漏洞（3 个：CVE-2022-3602、CVE-2023-44487、CVE-2023-41051）
  - 许可证汇总（Apache-2.0、MIT、BSD-3-Clause、LGPL-2.1、GPL-2.0）
  - 外部参考（构建系统、发布、issue 跟踪、VCS）

#### 1.2.2 SBOM 管理
- **更新频率**: 每月更新，或依赖变更时立即更新
- **工具升级**: 生产环境安装 `syft` 或 `cdxgen` 自动生成
- **漏洞监控**: 每周运行 `pip-audit`、`safety` 扫描依赖漏洞
- **Dependabot**: 启用 GitHub Dependabot 自动监控依赖更新

### 1.3 定义漏洞修复 SLA

#### 1.3.1 SLA 标准
- **状态**: ✅ 已完成 (`docs/security/VULNERABILITY_SLA.md`)
- **漏洞分级**: Critical / High / Medium / Low / Info（基于 CVSS 评分）
- **沙盒特定加权**: 沙盒逃逸、隔离绕过、审计链篡改、权限提升、密钥泄漏上调一级
- **标准修复时限**:
  - Critical: 响应 24h / 修复 7 天 / 发布 24h
  - High: 响应 48h / 修复 14 天 / 发布 72h
  - Medium: 响应 7 天 / 修复 30 天
  - Low: 响应 30 天 / 修复 90 天
- **沙盒逃逸特别 SLA**:
  - StrongPool 逃逸: 响应 4h / 修复 72h
  - LightPool 逃逸: 响应 8h / 修复 7 天
  - seccomp 绕过: 响应 8h / 修复 7 天

#### 1.3.2 漏洞响应流程
- 接收 → 分析 → 缓解 → 修复 → 发布 → 复盘（六阶段流程）
- 漏洞披露政策：私下报告、协调披露、90 天修复窗口
- 漏洞赏金：如启用，按等级给予奖励
- SLA 违规处理：记录、升级、通报、复盘、补偿

## 第二阶段：硬化流程（3-6 个月）

### 阶段目标
将安全政策落地到实际流程中，确保所有操作有证据留存，完成正式风险评估，并邀请审计机构进行预审计。

### 2.1 固化证据

#### 2.1.1 代码合并审批记录
- **目标**: 所有代码合并都留有审批记录
- **措施**:
  - GitHub Branch Protection：main 分支强制 PR 审查
  - 至少 1 名审查者批准（安全相关变更 2 名）
  - CI 必须全部通过才能合并
  - 合并记录保留至少 1 年
- **验证**: 随机抽查 10 个 PR，确认都有审批记录

#### 2.1.2 生产发布审批记录
- **目标**: 所有生产发布都留有审批记录
- **措施**:
  - 生产发布必须经过项目负责人审批
  - 发布前必须完成：全量测试、SAST、渗透测试、漏洞评估
  - 发布必须有版本号和变更说明
  - 发布记录保留至少 3 年
  - 支持回滚：发布失败必须能在 30 分钟内回滚
- **验证**: 随机抽查 5 个发布版本，确认都有审批记录

#### 2.1.3 安全配置变更记录
- **目标**: 所有安全配置变更都有记录和审批
- **措施**:
  - seccomp 白名单、eBPF 规则、网络策略变更必须经安全团队审批
  - 变更必须有测试验证
  - 变更必须有回滚方案
  - 变更记录记入审计日志
- **验证**: 随机抽查 5 个安全配置变更，确认都有审批记录

#### 2.1.4 审计日志完整性
- **目标**: 所有安全相关操作都有审计日志，且不可篡改
- **措施**:
  - HMAC 链式签名，每条日志包含前一条的哈希
  - 本地 spool 持久化，支持断电恢复
  - 定期校验审计链完整性
  - 审计日志保留至少 180 天
  - 审计日志仅授权人员可访问
- **验证**: 运行审计链完整性校验脚本，确认无篡改

### 2.2 执行风险评估

#### 2.2.1 威胁建模
- **目标**: 完成正式的威胁建模文档
- **方法**: 使用 STRIDE 方法（Spoofing、Tampering、Repudiation、Information Disclosure、DoS、Elevation of Privilege）
- **范围**:
  - StrongPool(MicroVM) 攻击面
  - LightPool 攻击面
  - eBPF 网络模块攻击面
  - gRPC 控制平面攻击面
  - 红蓝对抗框架攻击面（RealDataAdapter 输入污染）
  - 进化-防御桥接器攻击面（规则下发篡改）
- **交付物**: `docs/security/THREAT_MODEL.md`

#### 2.2.2 风险评估报告
- **目标**: 完成正式的风险评估报告
- **内容**:
  - 资产清单（代码、数据、基础设施、密钥）
  - 威胁清单（内部威胁、外部威胁、供应链威胁）
  - 漏洞清单（已发现漏洞、潜在漏洞）
  - 风险评估矩阵（可能性 × 影响）
  - 风险分级（Critical/High/Medium/Low）
  - 风险缓解措施
  - 残余风险评估
  - 风险接受声明
- **交付物**: `docs/security/RISK_ASSESSMENT_REPORT.md`
- **审批**: 项目负责人签字接受残余风险

#### 2.2.3 业务影响分析
- **目标**: 评估安全事件对业务的影响
- **内容**:
  - StrongPool 故障的业务影响
  - LightPool 故障的业务影响
  - 审计链中断的业务影响
  - 数据泄露的业务影响
  - 服务中断的业务影响（RTO/RPO）
- **交付物**: `docs/security/BUSINESS_IMPACT_ANALYSIS.md`

### 2.3 第三方审计预检查

#### 2.3.1 预审计准备
- **目标**: 邀请审计机构进行"预审计 (Readiness Assessment)"
- **准备材料**:
  - ✅ 信息安全政策
  - ✅ 安全编码规范
  - ✅ 漏洞修复 SLA
  - ✅ SBOM
  - ✅ 安全自评估报告 (`docs/audit/SECURITY_SELF_ASSESSMENT.md`)
  - ⏳ 威胁模型文档
  - ⏳ 风险评估报告
  - ⏳ 业务影响分析
  - ⏳ 审批记录样本
  - ⏳ 审计日志样本
  - ⏳ 事件响应记录样本

#### 2.3.2 预审计执行
- **目标**: 发现与正式审计的差距
- **范围**:
  - 文档完整性审查
  - 流程执行情况抽查
  - 技术控制验证
  - 证据留存检查
- **交付物**: 预审计报告（差距清单、改进建议、优先级）
- **后续行动**: 根据预审计报告修复差距，为正式审计做准备

#### 2.3.3 审计机构选择
- **候选方向**:
  - 专注虚拟化/云原生安全的厂商
  - 做过 Firecracker/KVM 沙盒、容器逃逸审计的团队
  - 有 SOC 2 / ISO 27001 认证资质的机构
- **评估标准**:
  - 相关项目经验
  - 审计师资质（CISSP、CISA、OSCP 等）
  - 行业口碑
  - 报价和周期
- **预算参考**: 完整底层沙盒+上层 Python 模块审计，几十万级别，周期 4-8 周

### 2.4 第二阶段验收标准

| 验收项 | 状态 | 验证方式 |
|--------|------|---------|
| 代码合并审批记录完整 | ⏳ | 抽查 10 个 PR |
| 生产发布审批记录完整 | ⏳ | 抽查 5 个版本 |
| 安全配置变更记录完整 | ⏳ | 抽查 5 个变更 |
| 审计日志完整性验证 | ⏳ | 运行完整性校验脚本 |
| 威胁模型文档完成 | ⏳ | 文档存在，经评审 |
| 风险评估报告完成 | ⏳ | 文档存在，负责人签字 |
| 业务影响分析完成 | ⏳ | 文档存在 |
| 预审计完成 | ⏳ | 预审计报告存在 |
| 预审计差距修复 | ⏳ | 差距清单全部关闭 |

## 第三阶段：正式审计（6-12 个月）

### 阶段目标
在真实裸机环境完成 StrongPool 的所有验证，启动 SOC 2 Type II 或 ISO 27001 的正式认证流程，完成独立第三方安全审计。

### 3.1 通过 KVM 验证

#### 3.1.1 裸机环境准备
- **硬件要求**:
  - x86_64 CPU，支持 KVM 硬件虚拟化（Intel VT-x / AMD-V）
  - 内存 ≥ 4GB（推荐 16GB+）
  - 磁盘：SSD 优先
  - 网络：千兆以上
- **软件要求**:
  - Linux 内核 ≥ 5.15（推荐 6.1 LTS / 6.6 LTS）
  - 必须开启：CONFIG_NAMESPACES、CONFIG_CGROUPS、CONFIG_SECCOMP、CONFIG_SECCOMP_FILTER、CONFIG_LANDLOCK、CONFIG_BPF、CONFIG_BPF_SYSCALL、CONFIG_KVM
  - cgroup v2 unified hierarchy
  - root/sudo 权限
- **依赖安装**:
  - `firecracker`（≥ 1.5）
  - `criu`（≥ 3.18）
  - `libbpf-dev`、`bpfcc-tools`
  - `libgrpc++-dev`、`protobuf-compiler-grpc`
  - `libssl-dev`（≥ 3.0.7）
  - `clang`、`libfuzzer`（模糊测试）

#### 3.1.2 裸机验证执行
- **验证脚本**: `scripts/verify_baremetal.sh`
- **验证模块**（10 大模块）:
  1. ✅ 基础环境检测（内核、cgroup v2、KVM、CAP_BPF）
  2. ⏳ LightPool namespace 隔离验证
  3. ⏳ seccomp 系统调用过滤验证
  4. ⏳ Landlock 文件系统限制验证
  5. ⏳ cgroup v2 资源限制验证
  6. ⏳ eBPF 网络过滤验证
  7. ⏳ StrongPool Firecracker MicroVM 创建/执行/销毁验证
  8. ⏳ CRIU 快照恢复验证
  9. ⏳ gRPC C++ 服务端端到端验证
  10. ⏳ 四层控制平面完整链路验证
- **预期结果**: 全部模块 PASS
- **SKIP 说明**: 内核/权限缺失时标记 SKIP，不代表失败
- **FAIL 处理**: 环境不满足或代码 bug，必须修复后重新验证

#### 3.1.3 压力测试与故障注入
- **压力测试**:
  - 高并发 VM 创建/销毁（100+ 并发）
  - 长时间运行（72 小时稳定性测试）
  - 资源耗尽测试（CPU/内存/磁盘/网络）
- **故障注入**:
  - 杀掉 worker 进程
  - 杀掉 VM
  - OOM 模拟
  - 网络中断
  - 磁盘满
- **验证目标**:
  - 资源回收完整性（无僵尸进程、无 fd 泄漏、无内存泄漏）
  - 审计完整性（故障期间审计日志不丢失）
  - 服务可用性（故障后能自动恢复）

#### 3.1.4 逃逸对抗测试
- **测试内容**:
  - 公开 namespace/seccomp 逃逸 POC 对抗测试
  - eBPF 过滤绕过测试
  - StrongPool MicroVM 逃逸测试
  - 内网访问拦截对抗测试
- **工具**:
  - 公开逃逸 POC 库
  - 自定义攻击用例（红蓝对抗框架生成）
  - libFuzzer 模糊测试
- **预期结果**: 所有逃逸尝试被拦截，无成功逃逸

### 3.2 启动正式审计

#### 3.2.1 认证选择
- **选项 A: SOC 2 Type II**
  - 适用场景：面向美国市场、SaaS 服务
  - 审计周期：6-12 个月（Type II 需要 6 个月观察期）
  - 审计内容：信任服务标准（安全、可用性、保密性、处理完整性、隐私）
  - 优势：国际认可度高，SaaS 行业标配
- **选项 B: ISO 27001**
  - 适用场景：面向全球市场、企业级客户
  - 审计周期：6-12 个月
  - 审计内容：信息安全管理体系（ISMS）
  - 优势：全球通用，企业级客户普遍要求
- **建议**: 根据目标市场选择，如资源充足可同时申请

#### 3.2.2 正式审计流程
1. **审计启动会**: 确定审计范围、时间、人员
2. **文档审查**: 审查所有安全文档、政策、流程
3. **现场审计**:
   - 访谈关键人员（管理员、开发者、运维、安全）
   - 抽查审批记录、审计日志、事件响应记录
   - 技术控制验证（渗透测试、漏洞扫描、配置检查）
4. **审计发现**: 输出审计发现（不符合项、观察项、改进建议）
5. **整改**: 修复不符合项，提供整改证据
6. **复核**: 审计机构验证整改效果
7. **出具报告**: 颁发认证证书/审计报告
8. **持续合规**: 每年监督审计，每 3 年重新认证

#### 3.2.3 独立第三方安全审计
- **审计范围**（详见 `docs/audit/SECURITY_SELF_ASSESSMENT.md`）:
  - 底层沙盒（C++）：LightPool、StrongPool、eBPF、控制平面
  - 上层进化框架（Python）：红蓝对抗、真实信号消费、进化-防御桥接器
  - 量子启发安全模块
  - 审计链与安全控制
- **审计重点**:
  - 沙盒逃逸路径
  - 控制平面漏洞
  - 权限绕过
  - 红蓝对抗逻辑污染风险
  - RealDataAdapter 输入污染
  - 进化规则下发篡改
- **交付物**:
  - 正式审计报告（风险分级、复现步骤、POC、修复建议）
  - 每一条漏洞必须可复现
  - 修复后再确认
  - 公开审计报告（经同意）

### 3.3 持续合规

#### 3.3.1 持续监控
- **安全监控**:
  - 7x24 安全事件监控
  - 异常行为检测
  - 入侵检测系统（IDS）
- **合规监控**:
  - 定期内部审计（每季度）
  - 控制有效性测试
  - 证据留存检查
- **漏洞监控**:
  - 每周依赖漏洞扫描
  - 每月 SAST 全量扫描
  - 每季度渗透测试

#### 3.3.2 持续改进
- **安全培训**: 每年至少一次安全意识培训
- **政策更新**: 每年审查更新安全政策
- **技术升级**: 定期升级依赖、内核、Firecracker
- **流程优化**: 根据审计发现和事件复盘持续改进

#### 3.3.3 透明公开
- **安全公告**: 及时发布安全公告
- **透明度报告**: 每年发布透明度报告（漏洞统计、SLA 达标率、审计结果）
- **开源审计**: 审计报告（经脱敏）公开在仓库
- **用户沟通**: 定期向用户通报安全状态

### 3.4 第三阶段验收标准

## 风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| 裸机环境获取困难 | 高 | 高 | 提前准备裸金属服务器或云厂商裸金属实例；嵌套虚拟化仅用于开发调试 |
| 审计预算不足 | 中 | 高 | 申请 OpenSSF 开源审计资助；上线漏洞赏金计划；分阶段审计 |
| 审计发现大量漏洞 | 中 | 中 | 提前完成内部 SAST/渗透测试；预留充足整改时间 |
| 认证周期延长 | 中 | 中 | 提前准备文档和证据；选择有经验的审计机构；预留缓冲时间 |
| 关键人员离职 | 低 | 高 | 知识文档化；交叉培训；至少 2 人掌握关键流程 |
| 上游依赖漏洞 | 高 | 中 | 每周依赖漏洞扫描；及时升级；SBOM 管理 |
