# PhotonBox 安全应急响应预案

> **版本**：1.0
> **生效日期**：2026-09-05
> **适用范围**：PhotonBox 所有生产部署环境（LightPool / StrongPool）
> **优先级**：P0 — 公网上线硬性必要条件

---

## 一、风险声明

### 1.1 已识别的致命风险

| 风险场景 | 影响范围 | 响应窗口 | 当前状态 |
|---------|---------|---------|---------|
| KVM MicroVM 0-day 逃逸 | 全部 StrongPool 实例 | **≤15分钟** | ⚠️ 无专职响应团队 |
| LightPool seccomp 绕过 | 全部 LightPool 实例 | **≤30分钟** | ⚠️ 无专职响应团队 |
| 控制平面 gRPC 鉴权绕过 | 全部沙箱管理面 | **≤15分钟** | ⚠️ 无专职响应团队 |
| 供应链投毒（依赖CVE） | 全部实例 | **≤2小时** | ✅ 有 CVE 监控脚本 |
| 红蓝对抗规则污染 | 防御规则有效性 | **≤1小时** | ⚠️ 无人工审核机制 |

### 1.2 诚实声明

**PhotonBox 当前没有专职 Oncall 轮值、没有安全应急响应团队。**

这意味着：
- 一旦 KVM 微虚机出现 0-day 逃逸漏洞，**没有任何人能在 15 分钟内响应**
- 漏洞修复依赖社区上游（Firecracker / Linux 内核），**修复周期不可控**
- 生产环境可能在数小时甚至数天内处于暴露状态

**本预案的目标**：在没有专职团队的情况下，通过自动化熔断、预定义SOP、外部支持渠道，将响应窗口从"无人能修"压缩到"机器自动止血 + 社区/商业支持兜底"。

## 二、应急响应组织架构

### 2.1 角色定义（最小化配置）

即使没有专职团队，也必须明确以下角色的**代理人**（可以是同一人，但必须有明确职责）：

| 角色 | 职责 | 最低要求 | 建议人选 |
|------|------|---------|---------|
| **应急指挥官** | 事件分级、决策升级、对外沟通 | 7×24 可联系 | 项目负责人 |
| **技术响应人** | 漏洞分析、补丁开发、热修复部署 | 熟悉 C++/Python/KVM | 核心开发者 |
| **运维执行人** | 熔断操作、实例隔离、配置回滚 | 有生产环境权限 | 运维负责人 |
| **安全顾问**（外部） | 漏洞验证、攻击面评估 | 第三方安全厂商 | 签约/合作 |

### 2.2 升级路径

```
P0 事件（逃逸/接管）
    ↓ 立即
应急指挥官 → 启动熔断 → 通知所有角色
    ↓ 15分钟内
技术响应人 → 漏洞分析 → 临时缓解措施
    ↓ 1小时内
运维执行人 → 全量部署缓解措施
    ↓ 持续
安全顾问 → 漏洞验证 → 攻击面评估
    ↓ 修复后
应急指挥官 → 验证修复 → 事件复盘
```

### 2.3 联系方式模板

> **必须在生产环境部署前填写以下信息，并在 README 中公开：**

```
紧急联系人：[姓名] / [电话] / [邮箱]
备用联系人：[姓名] / [电话] / [邮箱]
安全顾问：[厂商名称] / [24小时热线] / [邮箱]
上游社区：Firecracker GitHub Issues / Linux Kernel Security Mailing List
漏洞报告：GitHub Security Advisories / [安全邮箱]
```

## 三、自动化熔断机制

### 3.1 设计原则

**机器自动止血 > 人工响应**。在没有人能立即响应的情况下，系统必须能自动检测并隔离异常。

### 3.2 熔断触发条件

| 触发条件 | 检测方式 | 熔断动作 | 恢复条件 |
|---------|---------|---------|---------|
| seccomp 违规率突增 | 审计日志统计（>100次/分钟） | 暂停新实例创建 | 违规率恢复正常 + 人工确认 |
| VM-Exit 异常事件 | KVM 统计（VMCALL/MSR_WRITE异常） | 销毁可疑实例 | 人工确认无逃逸 |
| 进程尝试 ptrace/mount | seccomp 拦截日志 | 立即杀死进程 + 告警 | N/A（进程已死） |
| 网络连接异常 | eBPF 监控（连接到已知C2） | 断网 + 隔离实例 | 人工确认 |
| 资源使用异常 | cgroup 监控（CPU/内存突增3倍） | 限制资源 + 告警 | 资源恢复正常 |
| 红蓝对抗规则置信度骤降 | 进化漂移监控 | 冻结规则更新 + 回滚 | 人工审核 |

### 3.3 熔断级别

| 级别 | 名称 | 动作 | 影响范围 |
|------|------|------|---------|
| L1 | 实例级熔断 | 销毁/隔离单个可疑实例 | 单实例 |
| L2 | 节点级熔断 | 暂停节点上新实例创建 | 单节点 |
| L3 | 集群级熔断 | 全集群暂停 StrongPool，降级到 LightPool | 全集群 |
| L4 | 紧急熔断 | 全集群暂停所有不可信代码执行 | 全集群 |

### 3.4 熔断回滚

- **自动回滚**：L1/L2 熔断在触发条件消失后 5 分钟自动恢复
- **人工确认**：L3/L4 熔断必须由应急指挥官人工确认后才能恢复
- **回滚保护**：熔断后 1 小时内不允许自动恢复（防止反复触发）

## 四、漏洞响应 SOP

### 4.1 漏洞发现 → 修复 完整流程

```
阶段1：发现与确认（0-15分钟）
  ├─ 1.1 接收漏洞报告（内部监控/外部报告/上游公告）
  ├─ 1.2 验证漏洞可复现性（POC/日志/流量）
  ├─ 1.3 评估影响范围（哪些模块/版本/部署受影响）
  └─ 1.4 事件分级（P0/P1/P2/P3）

阶段2：应急止血（15-60分钟）
  ├─ 2.1 启动自动化熔断（L1-L4，按影响范围）
  ├─ 2.2 部署临时缓解措施（配置变更/规则更新/网络隔离）
  ├─ 2.3 通知受影响用户（如果涉及数据泄露）
  └─ 2.4 保留取证证据（日志/内存快照/磁盘镜像）

阶段3：漏洞修复（1-72小时，按SLA）
  ├─ 3.1 漏洞根因分析（代码路径/攻击向量/利用条件）
  ├─ 3.2 开发补丁（最小化修复 + 回归测试）
  ├─ 3.3 补丁验证（单元测试/集成测试/渗透测试）
  ├─ 3.4 灰度部署（10% → 50% → 100%）
  └─ 3.5 监控修复效果（漏洞不再可利用 + 无性能退化）

阶段4：事后复盘（修复后7天内）
  ├─ 4.1 时间线还原（从发现到修复的完整时间线）
  ├─ 4.2 根因分析（为什么会发生/为什么没提前发现）
  ├─ 4.3 改进措施（代码/流程/监控/文档）
  ├─ 4.4 更新威胁模型和攻击面清单
  └─ 4.5 公开漏洞报告（CVE/GitHub Security Advisory）
```

### 4.2 漏洞修复 SLA

| 漏洞等级 | 定义 | 修复SLA | 临时缓解SLA | 公开披露SLA |
|---------|------|---------|------------|------------|
| **P0 Critical** | 沙箱逃逸/控制平面接管/数据泄露 | 72小时 | 1小时 | 修复后7天 |
| **P1 High** | 权限绕过/拒绝服务/信息泄露 | 7天 | 4小时 | 修复后30天 |
| **P2 Medium** | 安全加固不足/配置缺陷 | 30天 | 24小时 | 修复后90天 |
| **P3 Low** | 最佳实践偏离/信息性问题 | 90天 | N/A | 随版本发布 |

### 4.3 逃逸类特别 SLA

| 逃逸类型 | 修复SLA | 临时缓解SLA | 熔断级别 |
|---------|---------|------------|---------|
| StrongPool KVM 逃逸 | 72小时 | 15分钟 | L3（全集群降级LightPool） |
| LightPool seccomp 绕过 | 72小时 | 30分钟 | L2（节点级暂停） |
| 控制平面 gRPC 鉴权绕过 | 24小时 | 15分钟 | L4（紧急熔断） |
| eBPF 过滤逻辑绕过 | 72小时 | 1小时 | L2 |

## 六、监控与告警

### 6.1 必须监控的安全指标

| 指标 | 监控方式 | 告警阈值 | 告警级别 |
|------|---------|---------|---------|
| seccomp 违规率 | 审计日志聚合 | >100次/分钟 | P1 |
| VM-Exit 异常率 | KVM 统计 | >10次/分钟 | P1 |
| 实例异常销毁率 | 沙箱管理日志 | >5次/分钟 | P2 |
| 进程 ptrace/mount 尝试 | seccomp 拦截日志 | 任何一次 | P0 |
| 网络连接到已知C2 | eBPF 流量监控 | 任何一次 | P0 |
| 红蓝对抗规则置信度 | 进化漂移监控 | 连续10轮<1% | P2 |
| 审计链HMAC异常 | 审计模块自检 | 任何一次 | P0 |
| 控制平面gRPC鉴权失败 | gRPC 日志 | >5次/分钟 | P1 |

### 6.2 告警渠道

- **P0 告警**：电话 + 短信 + 邮件 + IM（必须 15 分钟内响应）
- **P1 告警**：短信 + 邮件 + IM（必须 1 小时内响应）
- **P2 告警**：邮件 + IM（必须 24 小时内响应）
- **P3 告警**：邮件（每周汇总）

### 6.3 告警静默规则

- 计划内维护：提前 24 小时申请静默，最长 4 小时
- 已知漏洞缓解期：可静默相关告警，但必须有跟踪工单
- 禁止静默：P0 告警永远不允许静默

## 七、取证与证据保留

### 7.1 必须保留的证据

| 证据类型 | 保留方式 | 保留期限 |
|---------|---------|---------|
| 审计日志 | 不可变存储（WORM） | ≥180天 |
| 沙箱实例日志 | 集中日志系统 | ≥90天 |
| 网络流量 | eBPF 抓包（异常时触发） | ≥30天 |
| 内存快照 | 可疑实例销毁前自动 dump | ≥90天 |
| 磁盘镜像 | 受影响实例根文件系统 | ≥180天 |
| 配置变更记录 | Git 版本控制 + 审计日志 | 永久 |

### 7.2 证据完整性

- 所有证据必须附带 SHA256 哈希
- 审计日志必须有 HMAC 链（防篡改）
- 证据访问必须有审计记录（谁在什么时候访问了什么）
- 法律事件中，证据必须符合司法取证标准

## 八、演练与持续改进

### 8.1 应急演练

| 演练类型 | 频率 | 参与角色 | 验证内容 |
|---------|------|---------|---------|
| 桌面推演 | 每季度 | 全部角色 | 决策流程/沟通渠道/SOP执行 |
| 红蓝对抗 | 每半年 | 技术响应人/安全顾问 | 漏洞发现/熔断/修复全流程 |
| 故障注入 | 每月 | 运维执行人 | 熔断机制/自动恢复/监控告警 |
| 漏洞复现 | 每季度 | 技术响应人 | 已知漏洞POC复现/修复验证 |

### 8.2 持续改进

- 每次安全事件后 7 天内完成复盘报告
- 每季度更新威胁模型和攻击面清单
- 每半年更新应急响应预案
- 每年进行一次完整的第三方安全审计
