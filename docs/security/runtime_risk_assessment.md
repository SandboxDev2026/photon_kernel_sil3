# 沙盒运行时风险评估报告

**版本**: v1.0
**日期**: 2026-09-03
**范围**: PhotonBox 全部运行时后端（LightPool / StrongPool / gVisor / Wasm）
**性质**: 设计固有风险 + 工程实现风险 + 运维部署风险

---

## 执行摘要

PhotonBox 支持多种运行时后端，每种后端在安全性、性能、兼容性、部署成本之间有不同的权衡。本报告系统梳理 7 大类风险，每类给出风险描述、影响评估、缓解措施和代码层面的防护点。

**核心结论**:
- 没有"完美"的运行时：LightPool 快但共享内核，StrongPool 安全但资源开销大，gVisor 折中但有兼容问题，Wasm 安全但能力有限
- 最危险的风险不是技术本身，而是**配置错误和代码 bug 导致的安全降级**（第 4 点）
- 原型项目最大的风险是**未经过大规模生产验证**（第 5 点）
- 建议采用**风险分级调度**：不可信代码强制 StrongPool，可信代码可用 LightPool，绝不允许人为配置绕过

---

## 风险 1：强隔离后端全部依赖特权裸机环境

### 风险描述

| 后端 | 必需特权 | 普通容器可用性 |
|------|---------|--------------|
| LightPool | CAP_SYS_ADMIN（namespace/pivot_root/cgroup） | ❌ 非特权 Pod 不可用 |
| StrongPool | /dev/kvm + CAP_NET_ADMIN（tap 网卡） | ❌ 绝大多数云容器无 KVM |
| gVisor | 部分 capabilities + 用户命名空间 | ⚠️ 部分可用，但用户命名空间改变内核行为 |
| Wasm | 无特殊特权 | ✅ 可用 |

### 影响

- 部署成本高：不能随便跑在普通 Serverless、容器平台、CI 环境
- `docker --privileged` 不建议做功能验证：用户命名空间会改变内核行为，测不出真实逃逸边界
- 开发调试困难：开发者本地环境可能无法运行完整能力

### 缓解措施

1. **能力探测矩阵**（已实现）：启动时逐项探测 KVM/CAP_BPF/CAP_SYS_ADMIN/namespace，输出能力报告
2. **优雅降级**（已实现）：缺少能力时自动关闭对应模块，不崩溃
3. **安全降级硬规则**（已实现）：高风险任务无 KVM 时直接拒绝，不静默降级到 LightPool
4. **部署文档**：`docs/privileged_e2e_guide.md` 提供完整特权环境部署指南

### 代码防护点

- `RiskEnforcer`：不可信输入强制 StrongPool，无 KVM 拒绝
- `CapabilityProbe`：启动时能力探测，结果写入 metrics

---

## 风险 2：StrongPool（Firecracker）资源开销大

### 风险描述

- **内存开销**：每个 VM 固定基础内存开销（裁剪内核 + VM 内存，5-15MB 基础 + 业务内存）
- **CPU 抖动**：频繁创建销毁 VM 带来 CPU 上下文切换和缓存失效
- **快照复杂度**：UFFD（用户态缺页处理）机制本身有复杂度，bug 调试难度高
- **单机并发上限**：被内存限制，10000 实例需要 50-150GB 内存

### 影响

- 大批量遗传算法种群评估时，VM 创建销毁开销显著
- 内存超配可能导致 OOM，影响宿主机上其他服务
- 快照恢复 bug 可能导致 VM 状态不一致或内存泄漏

### 缓解措施

1. **快照预启动池**（已实现配置）：`snapshot_pool_size=8`，预启动一批 VM 待命
2. **短生命周期设计**：任务执行完立刻销毁 VM，不常驻闲置
3. **单机并发上限**（已实现）：`calculate_max_concurrent_vms()` 基于可用内存计算
4. **30% 内存缓冲**（已实现）：`memory_reserve_ratio=0.30`，预留内存防止 OOM
5. **风险分级调度**（已实现）：低风险任务走 LightPool，只有高风险才走 StrongPool

### 代码防护点

- `StrongPoolConfig::calculate_max_concurrent_vms()`：自动计算最大并发
- `StrongPoolConfig::memory_reserve_ratio`：30% 内存缓冲
- VM TTL：30 秒强制销毁，防止僵死 VM 泄漏

## 风险 3：gVisor 后端短板

### 风险描述

- **IO 性能损耗**：IO 密集场景有 15-30% 性能损耗（每次 syscall 都要经过用户态内核拦截）
- **syscall 不兼容**：部分系统调用没有实现，有些 Python 脚本、二进制直接报错崩溃
- **调试困难**：gVisor 的 syscall 兼容问题非常耗时间，需要熟悉 gofer、sentry 架构

### 影响

- 不适合 IO 密集型任务（大量文件读写、网络通信）
- 部分第三方库可能因缺少 syscall 而崩溃
- 排查"为什么这个脚本在 gVisor 里跑不起来"非常耗时

### 缓解措施

1. **运行时选择器**：根据任务特征自动选择后端，IO 密集任务不选 gVisor
2. **syscall 兼容性探测**：任务执行前探测所需 syscall，gVisor 不支持时自动切换后端
3. **降级路径**：gVisor 执行失败时自动降级到 StrongPool（不降级到 LightPool）
4. **文档标注**：明确 gVisor 适用场景和已知不兼容列表

### 代码防护点

- `RuntimeSelector`：根据任务风险等级和特征选择后端
- gVisor 执行失败 → 降级到 StrongPool（不降级到 LightPool）

## 风险 4：LightPool 存在根本性安全风险（最高优先级）

### 风险描述

- **共享宿主机内核**：就算 seccomp + Landlock 拉满，遇到内核 UAF、eBPF 漏洞依旧可以逃逸
- **设计上要求**：不可信代码禁止使用 LightPool
- **实际风险**：人为配置错误、代码 bug 有可能绕过 RuntimeSelector 规则，把恶意任务送到 LightPool

### 攻击场景

```
攻击者构造恶意任务
    ↓
RuntimeSelector 因 bug/配置错误选择 LightPool
    ↓
恶意代码在 LightPool 中执行（共享宿主内核）
    ↓
利用内核 0day 逃逸到宿主机
    ↓
横向移动、数据窃取、持久化
```

### 影响

- 这是**最危险的风险**：一旦安全降级被绕过，所有隔离防线失效
- 内核 0day 在野利用时，LightPool 等于无防护
- 人为配置错误（如管理员为了性能手动关闭强制 StrongPool）可能导致安全事故

### 缓解措施（多层防护，纵深防御）

#### 第 1 层：RuntimeSelector 强制规则（已实现）
- 不可信输入 → 强制 StrongPool
- 风险分数 > 70 → 强制 StrongPool
- 无 KVM → 拒绝任务（不降级到 LightPool）

#### 第 2 层：执行前二次校验（本次加固）
- Worker 执行前再次校验：不可信任务是否被分配到 LightPool
- 如果发现不可信任务在 LightPool 中，直接拒绝执行并告警
- 这一层防止 RuntimeSelector 的 bug 或配置错误绕过

#### 第 3 层：seccomp 白名单最小化（已实现）
- 即使逃逸到 LightPool，seccomp 白名单也限制可利用的 syscall
- 拦截 ptrace、kexec、io_uring、nf_tables 等高危 syscall

#### 第 4 层：审计告警（已实现）
- 不可信任务被分配到 LightPool 时触发 P0 告警
- 审计日志记录每次 RuntimeSelector 决策，便于事后追溯

#### 第 5 层：配置锁定（建议）
- 生产环境中"强制 StrongPool"配置不可通过 API 动态修改
- 需要重启服务并修改配置文件才能关闭，减少人为误操作

### 代码防护点（本次加固）

- `RuntimeGuard::verify_assignment()`：执行前二次校验，不可信任务在 LightPool 中直接拒绝
- 不可信任务分配到 LightPool → P0 告警 + 审计日志 + 拒绝执行

## 风险 5：原型带来的短板（重点）

### 风险描述

#### 5.1 没有真实线上大规模生产验证
- nsjail、Firecracker 是经过大规模线上锤炼的成熟项目
- PhotonBox 整套组合是设计原型，没有经过生产流量毒打
- 边界 case、极端负载、长时间运行的稳定性未知

#### 5.2 C++ 代码量巨大，自己维护成本高
- cgroup v2 管理、Firecracker 生命周期管理、eBPF 钩子、审计链路
- 每一块都有很多边界 bug：fd 泄漏、竞态条件、资源清理不完整
- C++ 内存安全问题（use-after-free、缓冲区溢出）

#### 5.3 故障排查复杂
- 沙盒卡死、VM 僵死、cgroup 泄漏、namespace 残留
- 需要熟悉 Linux 内核底层知识才能排错
- 缺少成熟的诊断工具和 runbook

#### 5.4 KVM 机器硬件兼容性坑
- 部分云实例 CPU 不支持虚拟化（/dev/kvm 不存在）
- 部分宿主机内核版本 bug 导致 Firecracker 不稳定
- 嵌套虚拟化（VM 里跑 KVM）性能差且不稳定

### 影响

- 生产环境可能遇到未发现的边界 bug
- 维护团队需要深厚的 Linux 内核和虚拟化知识
- 故障排查时间长，影响可用性
- 部署时可能遇到硬件兼容性问题

### 缓解措施

1. **诚实标注**：README 和文档明确标注"原型项目，未经过大规模生产验证"
2. **生产检查清单**：`PRODUCTION_CHECKLIST.md` 列出上线前必须完成的验证项
3. **应急响应 Runbook**：`docs/operations/incident_response_runbook.md` 提供故障处置流程
4. **能力探测**：启动时探测 KVM/内核版本/cgroup v2，不满足时明确告警
5. **建议**：对公网多租户场景，先进行第三方安全审计和小规模灰度验证

## 风险 6：网络模型复杂度高

### 风险描述

- StrongPool 每一个 VM 创建 tap 网卡
- 大批量 VM 会产生大量网络命名空间、tap 设备
- 需要处理网卡回收、防止宿主机网卡资源泄漏
- tap 设备创建/销毁有竞态条件，高并发时可能泄漏

### 影响

- 长时间运行后宿主机 tap 设备耗尽，无法创建新 VM
- 网络命名空间残留导致 `ip netns` 列表膨胀
- 网卡泄漏可能被攻击者利用进行网络嗅探

### 缓解措施

1. **资源清理守卫**（本次加固）：VM 销毁时强制清理 tap 设备和网络命名空间
2. **资源泄漏监控**：定期检查宿主机 tap 设备数量，超过阈值告警
3. **tap 设备池化**：预创建一批 tap 设备，VM 销毁时归还到池中而非销毁
4. **创建时幂等**：tap 设备创建前检查是否已存在，避免重复创建

### 代码防护点（本次加固）

- `NetworkResourceGuard`：VM 销毁时强制清理 tap/netns，异常时重试
- tap 设备数量监控指标：`photon_sandbox_tap_devices_total`

## 风险 7：Wasm 后端能力有限

### 风险描述

- Wasm 只能运行编译到 wasm 的程序
- 不能直接跑原生 ELF、普通 Python 脚本
- WASI 接口还在演进中，部分系统调用不支持
- 只能作为补充，不能替代其他后端

### 影响

- 适用场景有限：只适合执行可控的、编译好的 Wasm 模块
- 不能用于执行用户提交的任意 Python/Shell 代码
- 第三方库支持不完善

### 缓解措施

1. **明确定位**：Wasm 后端定位为"补充"，不是主力后端
2. **自动检测**：任务执行前检测是否为 Wasm 模块，不是则自动选择其他后端
3. **文档标注**：明确 Wasm 后端的适用场景和限制
4. **payload 执行器支持**：`PayloadType::WASM` 已支持 Wasm 模块执行

## 结论与建议

### 可以做的

1. ✅ 内网可信/半可信 Agent 场景：LightPool 足够，性能好
2. ✅ 公网不可信代码：StrongPool（KVM MicroVM），独立内核
3. ✅ 可控的 Wasm 模块：Wasm 后端，轻量安全
4. ✅ 开发测试：任意后端，能力探测自动降级

### 不建议做的

1. ❌ 公网多租户不可信代码跑 LightPool（内核 0day 风险）
2. ❌ 普通容器/Serverless 平台跑完整能力（缺特权）
3. ❌ 未经第三方安全审计直接对公网开放（原型项目）
4. ❌ IO 密集任务跑 gVisor（性能损耗大）

### 上线前必须完成

1. 🔴 第三方安全审计（SAST + 渗透测试 + 逃逸对抗）
2. 🔴 裸机 KVM 环境 StrongPool 端到端压测（72 小时稳定性）
3. 🟠 故障注入测试（VM 僵死、cgroup 泄漏、tap 泄漏）
4. 🟠 灰度发布：先 1% 流量，观察 1 周，再逐步扩大
5. 🟡 运维团队培训：Linux 内核、虚拟化、cgroup、namespace 排错
