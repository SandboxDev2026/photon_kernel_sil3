# PhotonBox 架构借鉴落地报告 v33

**日期**: 2026-09-03
**版本**: v33
**触发**: 用户指出核心问题——红蓝对抗尚未对接真实日志流，推演完未自动部署新防御规则到沙盒执行层
**核心落地**: AdversaryLoopOrchestrator 红蓝对抗闭环编排器

---

## 一、用户指出的核心问题

### 1.1 问题清单

| # | 问题 | 影响 |
|---|------|------|
| 1 | 尚未对接真实日志流（tail/gRPC事件推送未接入） | 红蓝对抗只能用模拟数据，无法从真实攻击中学习 |
| 2 | 推演完未自动把新防御规则部署到沙盒执行层 | 进化的防御规则停留在纸面，无法实际生效 |
| 3 | 高级能力极度依赖裸机环境 | 公有云普通实例拿不到/dev/kvm、eBPF权限 |
| 4 | 攻击面依然存在 | StrongPool不是银弹，Guest内核+Firecracker+KVM仍有CVE风险 |

### 1.2 解决方案

创建AdversaryLoopOrchestrator闭环编排器，将三大核心组件串联：
- RealtimeLogStream（真实日志消费）
- RedBlueAdversaryTrainer（红蓝对抗推演）
- DefenseRuleExecutor（防御规则部署）

形成完整闭环：真实日志流 → 红蓝对抗推演 → 自动部署新防御规则 → 沙盒执行层生效

## 二、AdversaryLoopOrchestrator 架构

### 2.1 整体架构

```
┌─────────────────┐     ┌──────────────────────┐     ┌─────────────────────┐
│ RealtimeLogStream│────▶│ RedBlueAdversaryTrainer│────▶│ DefenseRuleExecutor  │
│ (真实日志消费)    │     │ (红蓝对抗推演)         │     │ (防御规则部署)       │
└─────────────────┘     └──────────────────────┘     └─────────────────────┘
         ▲                        │                              │
         │                        ▼                              ▼
    日志源配置              新防御规则生成                    沙盒执行层
  (seccomp/VM-Exit/        (蓝方进化)                     (seccomp/eBPF/
   审计链)                                                  StrongPool配置)
```

### 2.2 核心组件

| 组件 | 行数 | 职责 |
|------|------|------|
| OrchestratorConfig | - | 编排器配置（日志源/推演/部署/安全） |
| OrchestratorStats | - | 编排器统计指标 |
| AdversaryLoopOrchestrator | 381 | 闭环编排器主类 |

### 2.3 三种推演触发模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| EVENT_DRIVEN | 每N个事件触发一次推演 | 高流量环境，实时响应 |
| TIMED | 每N秒定时推演 | 低流量环境，定期优化 |
| HYBRID | 事件驱动+定时（默认） | 通用场景，兼顾实时性和效率 |

### 2.4 自动部署安全机制

| 机制 | 说明 |
|------|------|
| 有效性过滤 | 只部署有效性≥阈值的规则（默认0.6） |
| 去重部署 | 已部署规则ID集合，防止重复部署 |
| 部署数量限制 | 每轮最多部署N条规则（默认10） |
| 默认dry-run | 部署模式默认DRY_RUN，生产环境需显式切换APPLY |
| 高危操作确认 | 高危部署需显式确认 |
| 失败自动回滚 | 部署失败自动回滚到上一版本 |
| 部署后验证 | 部署后验证配置是否正确应用 |

## 四、解决用户指出的四大问题

### 4.1 问题1：尚未对接真实日志流

**解决**：AdversaryLoopOrchestrator自动接入RealtimeLogStream，支持：
- 文件tail消费（seccomp/VM-Exit/审计链日志）
- gRPC流消费（框架实现）
- 多源汇聚（同时消费多个日志源）
- 事件回调（日志事件自动注入红蓝对抗）

### 4.2 问题2：推演完未自动部署

**解决**：AdversaryLoopOrchestrator自动部署闭环：
- 推演完成后自动提取新防御规则
- 有效性过滤+去重
- 通过DefenseRuleExecutor部署到沙盒执行层
- 部署后验证+失败回滚
- 部署审计日志

### 4.3 问题3：高级能力依赖裸机

**解决**：优雅降级机制：
- 配置目录权限回退（/etc/photonbox → ~/.photonbox → /tmp）
- 部署模式默认DRY_RUN（无特权环境也能运行）
- 日志流支持普通文件（不需要特殊权限）
- 红蓝对抗推演不依赖特权环境

### 4.4 问题4：攻击面依然存在

**解决**：持续监控+自动进化：
- 实时监控seccomp违规/VM-Exit/审计链异常
- 新攻击模式自动触发推演
- 逃逸事件高优先级立即推演
- 新防御规则自动部署
- 形成"攻击→检测→推演→防御→部署"的持续进化闭环

## 六、生产部署建议

### 6.1 部署模式切换

```python
# 开发/测试环境（默认，安全）
config = OrchestratorConfig(deploy_mode=ExecutionMode.DRY_RUN)

# 生产环境（需充分验证后切换）
config = OrchestratorConfig(
    deploy_mode=ExecutionMode.APPLY,
    min_rule_effectiveness=0.8,  # 提高阈值
    max_deploy_per_round=3,       # 限制每轮部署数
    require_confirmation_for_high_risk=True,
)
```

### 6.2 监控指标

编排器提供完整统计指标，可接入Prometheus：
- total_events_consumed：消费事件数
- total_training_rounds：推演轮数
- total_rules_generated：生成规则数
- total_rules_deployed：部署规则数
- total_deploy_failures：部署失败数
- total_rollbacks：回滚次数
- errors：错误数
